# 完整任务示例：用默认工作流完善贡献指南

本文使用 `/dsh-flow init` 安装的 [development-workflow.yaml](<development-workflow.yaml>)，在一个你有写权限的 GitHub 演示仓库中新增或完善贡献指南，走完 `create-issue → implement → review → test → merge`。**不需要新建 YAML 或另一套 workflow。**

这是操作示例，不是执行回执：本文没有实际运行该任务，不提供虚构的 Issue / PR 地址或成功截图。首页现有截图展示进阶配置、启动界面和 BLOCK 诊断，不是默认流程成功交付的证据。

## 1. 准备一个可写的演示仓库

先按[安装与上手](<../getting-started.md>)安装插件并启动 DSH Web。然后选择一个你可以创建 Issue、推送任务分支、创建 PR，并在确认后 squash 合并的 GitHub 仓库，建议使用无发布或部署自动化的独立演示仓库，而非生产项目。仓库应已有默认分支和至少一个提交。

本文中的 `<owner>/<repo>` **都是占位符**，必须替换为你实际拥有权限的完整仓库标识；`<本地仓库绝对路径>` 必须替换为该仓库的本地 Git 工作区。不要把本插件仓库或别人的仓库当作演示目标。

在终端中做只读核对（以下为 PowerShell，先替换两处占位符）：

```powershell
$repo = "<owner>/<repo>"
$workspace = "<本地仓库绝对路径>"
git -C "$workspace" status --short
git -C "$workspace" remote -v
gh auth status
gh repo view "$repo" --json nameWithOwner,defaultBranchRef,viewerPermission
```

确认远端确实对应目标仓库，默认分支存在，GitHub 身份具备相应权限。Git 推送认证、仓库保护及 squash 设置也必须允许后续操作；只读查询成功不保证这些写操作一定成功。建议从干净工作区开始；若有用户未提交或未跟踪内容，先明确保护边界，不让 Agent 自动清理或混入提交。

**启动前先理解并授权副作用：**实际运行会调用模型（可能计费），修改本地文件，并在 GitHub 创建真实 Issue、推送分支、创建或更新 PR、发布证据评论；最后还会在另行确认后合并并关闭 Issue。检查仓库自动化，避免 push、PR 或 merge 间接触发发布/部署；无法确认安全边界时先停下来。

若你只授权只读操作，不要照此启动：默认模板的验收要求包含真实建票、提交推送、PR 和合并，**不能在只读授权下保证完整交付**。只想阅读或检查配置，可以停在下文的 `list` / `check`。

## 2. 初始化、重启并建立 Manager 会话

在已经加载插件的 DSH 对话中依次执行，先检查预演输出，再决定实际写入：

```text
/dsh-flow init --dry-run
/dsh-flow init
```

这会安装通用 Manager preset 和 `development-workflow`。已有不同内容默认跳过；若提示差异，先核对本地内容，不用 `--force` 盲目覆盖，也不另建一份同名流程掩盖差异。此示例依赖上方链接中的默认五节点合同。

初始化后重启对应 DSH 实例并刷新页面，使用与安装时一致的 `DSH_HOME`。新建会话时：

1. 选择 **团队工作流 Manager（通用）** preset。
2. 将工作目录设为刚才核对的**目标演示仓库**，不是插件源码目录。
3. 为 Manager 选择可用模型及需要的思考档位。默认 developer、reviewer、tester 与 Judge 都继承 Run 启动时冻结的 Manager 模型路由，无需为本例修改 YAML。
4. 在该 Manager 会话中执行：

   ```text
   /dsh-flow list
   /dsh-flow check development-workflow
   ```

`list` 应能列出合法的 `development-workflow`；`check` 只做本地配置/模型路由检查，不发送真实模型推理请求。继承路由或检查被跳过，不等于模型已经实测可用；若报告误配或异常，先按[使用手册](<../user-guide.md>)排查。

## 3. 在启动弹窗粘贴完整任务

点击对话输入区的 **启动工作流**，选择 **`development-workflow`**。将下方完整文本复制到任务描述，**替换两处占位符**并确认授权内容与你的意图一致，再启动。不要另外执行一次 `/dsh-flow start`，否则是在重复尝试启动。

```text
请使用当前选定的 development-workflow，在以下唯一目标上完成一个仅文档任务：
GitHub 仓库：<owner>/<repo>
本地工作区：<本地仓库绝对路径>

目标：新增或完善仓库根目录 CONTRIBUTING.md，让首次贡献者知道如何准备环境、
提出 Issue、提交 PR，以及运行本项目现有的适用检查。已有贡献指南则最小补全，不重写无关内容。

请先调查真实仓库状态、远端默认分支、已有用户改动及项目规范，读取现有 README、
AGENTS.md（如有）、贡献文档、构建配置和 CI。先概括你理解的范围、验收和授权，
逐轮提出仍需我决定的问题；等我明确确认理解一致后再创建唯一 Issue。
命令必须来自这个目标项目的实际规范和配置，不要假设语言、包管理器或固定测试栈，
不要凭空写 npm test 等命令。若没有既有命令，明确说明并与我确认适用的检查方式。

范围：只修改根目录 CONTRIBUTING.md；不改业务代码、依赖、锁文件、CI、其他配置或文档。
发现必须扩大范围时暂停问我，不自行扩展。保护已有用户改动，不清理、不暂存无关文件。

验收：
1. 指南包含项目实际的环境/准备步骤、Issue 与 PR 提交流程、适用检查及其执行位置；
   不存在的项目机制要如实说明，不编造政策、命令或成功结果。
2. 文档引用的本地路径与链接有效，命令与项目现有规范一致；保留仍然有效的原内容。
3. 只产生上述文档差异；开发自检、独立 review 与 test 都按同一 Issue 验收，
   运行从项目调查确定的适用检查并记录真实命令/结果；不适用项必须说明依据。
   必需验证受阻则 BLOCK，不把未运行当通过，也不要因只改文档就一律免测。
4. Issue 持续记录规格、实现、审查、测试与交付证据；审查/测试绑定同一 PR 的确切 base/head SHA。

授权：在本次范围与验收经我确认后，允许在上述唯一仓库创建和更新一个 Issue、
从核对的远端默认分支创建一个任务分支、提交本任务文档、正常 push、创建或更新一个 PR，
并在该 Issue / PR 写必要说明和证据。返工复用同一任务分支与 PR，不造空提交。

这不是合并授权。到 merge 时必须先向我展示真实 PR 地址、确切 base/head SHA、
审查和测试证据，取得我明确绑定该 candidate 的再次确认后，才能使用 head 条件保护
执行 squash 合并，并核验实际结果、关闭关联 Issue。候选变化则旧确认失效，重走审查、测试与确认。
禁止绕过仓库保护、强推、删除分支、发布或部署，也禁止通过仓库自动化间接发布或部署。
冲突、权限、模型/环境问题、结果不明或仓库不支持 squash 时暂停交 Manager，不盲目重试写入。
```

启动后，`create-issue` 的 Manager 会先与你确认理解；回复时明确指出认可或需要修正的范围、验收与授权。不要为了推进而对未核实的内容一律回答“通过”。配置检查通过也不表示此任务已经执行。

## 4. 五个节点里应看到什么

流程串行执行；每个节点的结果还需独立 Judge 核验，不是 Agent 说“完成”就自动满足验收。Issue 是证据的持续入口，具体地址由本次真实运行产生。

| 节点 | 预期动作与可核验结果 | 需要返工或暂停时 |
| --- | --- | --- |
| `create-issue`（Manager） | 调查仓库/默认分支与用户改动，逐轮澄清；你明确确认后创建唯一开放 Issue，正文含范围、验收与远端授权，交接真实链接。 | 范围或权限不明先澄清；重入查询并复用已创建 Issue，不重复建票。 |
| `implement`（developer） | 从已核对的远端默认分支建立任务分支，最小修改贡献指南并运行适用自检；提交、正常推送，创建唯一 PR，向 Issue 写实现与检查证据、base/head SHA。 | 必修项在同一分支/PR 修复；必需验证受阻则 BLOCK，不冒充通过。 |
| `review`（reviewer） | 固定当前 PR base/head，独立检查完整差异、Issue 验收、项目规范和安全边界；Issue 留绑定修订的审查结论，通过后进入 `test`。 | 具体产品必修项用 `changes-required` 回 `implement`；候选变化用 `stale` 回实现重验；环境或权限障碍暂停。 |
| `test`（tester） | 针对已审查的同一 base/head 独立运行适用检查，逐项验证文档内容、链接和范围，记录真实结果及未测边界；全部满足才进入 `merge`。 | 产品缺陷回实现，之后重走 review/test；候选变化用 `stale` 回实现；缺少必需环境/权限不能算通过。 |
| `merge`（Manager） | 展示真实 PR、已审查/测试的 base/head 与证据；取得你针对该候选的明确确认，紧邻操作再次核对修订与保护；head 条件保护 squash 合并，核验实际结果，关闭 Issue 并记录交付。 | 未确认不合并；合并前候选变化回实现重走检查与确认；冲突、保护限制、不支持 squash 或结果不明则暂停，不重复合并。 |

例如，审查发现指南中的检查命令与仓库配置不符，应给出具体依据，回 `implement` 修正文档后重新审查、测试；这与 GitHub 网络不可用不同，后者应暂停处理环境，不把网络错误报成文档缺陷。默认模板不会因为一次返工而新建第二个 Issue 或 PR。

## 5. 合并确认与完成判断

收到合并询问时，先打开真实 PR 与 Issue 证据，核对差异只涉及授权文档，审查和测试对应同一候选。确认回复应明确标识该 PR 及展示的 base/head SHA；例如“我确认将刚才列出的 PR 按所列 base/head 候选 squash 合入已核对的默认分支”。若期间修订变化，必须重新检查，不能沿用这次批准。

通过 `/dsh-flow status` 查看状态；有配套侧栏时也可看工作流监控。最终应同时核对 `businessReturn` 为 `delivered`、最终交接中的真实合并结果和 Issue 关闭证据；不能仅凭 `completed` 字样或一张截图判断已交付。分支按本例约定保留，不执行部署或发布。

一个 workspace 最多一个活动 Run。遇到 BLOCK，先读取当前原因和已有证据，补足授权内的信息或解决障碍，再由 Manager 按当前工作单恢复；外部操作结果未知时先核验，不重复推送、建票或合并。详细命令、恢复与终止方式见[使用手册](<../user-guide.md>)。退出会话或终止流程都不代表已发生的文件修改、Issue、push、PR 或合并被撤销；额外回滚/清理需要另行确认。
