# 工作流监控布局与 Run 模型配置

- 日期：2026-11-11
- 状态：设计已确认；Q8 采用原会话换模修订方案，Q10–Q12 已确认；Q13 不做变更记录或审计，Q14 收敛为直接修改所选 Run 的角色模型，不设首次更新、升级或迁移操作。
- 范围：设计与文档，不代表实现、测试或部署完成；不操作真实 Run。

## 最终方案速览

**更紧凑的监控界面、独立双向滚动的记录表、仅影响所选未结束 Run 的角色主备编辑。** 不增加审计、迁移向导或额外 Run 控制功能。

宽屏结构示意（不是已实现截图；窄侧栏将概览两列上下堆叠）：

```text
Run 选择 · 状态 · 耗时                  刷新  模型配置
┌─────────────────────┬────────────────────────┐
│ 运行图              │ 当前执行               │
│                     │ 节点 / Role / 实际模型 │
│                     │ 状态 / BLOCK 原因      │
└─────────────────────┴────────────────────────┘
执行记录
┌──────────────────────────────────────────────┐
│ 固定表头；左侧记录身份列固定                  │
│ 记录……                         表内纵向滚动 ↕ │
│ ← 横向滚动条在表格可视窗口底部 →             │
└──────────────────────────────────────────────┘
▸ 启动 prompt    ▸ 完整节点列表    ▸ 详细材料
```

模型配置从顶栏按需打开，明确显示 Run 与工作区；按 Role / Judge 展示当前实际模型、保存的主备与待生效提示。选定角色后编辑主备及各自档位，使用“更新，下次从主模型开始”一次提交；不把表单常驻首屏，不提供配置变更历史。

核心场景：A 正在执行 → 为该角色保存 C/D → A 完成且安全收口 → 下一次新派发使用 C；C 遇到符合原规则的模型故障才切 D，之后沿用 D。再次主动更新就让下一次新派发重新从最新主模型开始。已登记的派发不变；未修改的角色、其他 Run 和模板不变。

## 需求与现状

用户希望工作流监控更美观、整齐；执行记录较多时，不必滚到全部记录末尾才能操作横向滚动；允许为当前 Run 的角色更新主备模型，正在执行的派发保持不变，后续使用最新配置。

当前源码与新需求有三处差异：

1. [监控样式](../../web-client/src/monitor.js#L93-L104)明确移除了表格最大高度，表格只横向滚动、纵向由整个监控面板承载，横向滚动条随全部记录下移。
2. [现换模入口](../../src/engine/engine.ts#L1687-L1747)设置的是人工救援路由 C，而非替换主备组合；普通 Role 正在执行时会拒绝替换。既有回退合同是 C → 冻结主 A → 冻结备 B。
3. 监控原本是只读入口。加入模型编辑需要明确人类写入授权，不能伪造 Manager 身份调用旧工具。

历史决策保留原记录，不把新需求伪装成原来就支持：

- [原展示方案](run-monitor-presentation.md)中的“表格不设最大高度、单一外层纵向滚动”被本次明确需求重新打开；保留外层可滚动能力，不能重现宿主容器裁切内容的问题。
- [ADR-0005](../adr/0005-run-monitor-sidebar-tab.md)的只读监控边界，按已确认 Q9 由[ADR-0006](../adr/0006-current-run-model-configuration.md)记录局部修订；不是授权任意 Run 控制操作。
- [ADR-0004](../adr/0004-role-model-fallback-authorization.md)的冻结主备及人工救援链与本次运行期配置诉求不同；已确认的替代原则记录于[ADR-0006](../adr/0006-current-run-model-configuration.md)。本次直接更新目标角色的 Run 配置，不引入用户可见的迁移阶段；旧 ADR 的实施状态仍代表当前代码。

## 第一轮已确认

### Q1：紧凑控制台布局

- 沿用宿主主题、组件与色彩语义，不新增独立视觉体系或装饰性大卡片。
- 顶部集中 Run 选择、状态、耗时与刷新信息；长 ID、路径降为次要信息，仍可查看完整值。
- 当前执行突出节点、Role、实际模型及 BLOCK 原因，与用户选中的历史详情分开。
- 运行图和执行记录形成清晰工作区；长 prompt、材料和判定详情按需展开，避免抢占首屏。
- 宽屏/窄侧栏的排布及模型编辑入口按已确认的 Q4。

### Q2：执行记录独立双向滚动

- 表格具有随视口调整的最大高度，目标约为视口高度的 1/2–2/3；记录较少时自然高度，不填充空白。
- 表格内部可以纵向和横向滚动；横向滚动条位于表格可视窗口底部，不再跟随全部记录末尾。
- 固定表头及左侧记录身份列；具体固定宽度需兼顾窄侧栏，不能遮住全部可滚动数据。
- 长文本截断但可查看完整内容；刷新保留选中记录及滚动位置。
- 使用原生滚动与 sticky 能力，复用现有表格，不引入表格框架。
- 外层监控仍可滚动，使图、记录及详情均可到达；不能以裁切外层来换取表格滚动。

### Q3：仅当前 Run 的 Role / Judge 模型配置

- 支持普通 Role 与 Judge，排除 Manager 主会话。
- 主模型、可选备用模型分别配置，各自保留独立思考强度。
- 区分本次实际使用的模型与待后续生效的配置，不能把配置显示成已经发生的派发事实。
- 只影响目标 Run，不改 catalog YAML、模板或其他 Run。
- 当前正在执行的派发不热切换；“下一次”的精确边界按已确认的 Q5。

## 第二轮已确认（Q8 按修订方案）

### Q4：响应式布局与模型配置入口

- 顶栏提供 Run 选择、状态、耗时、刷新和“模型配置”按钮。
- 概览区宽屏为运行图与当前执行并排，窄侧栏上下排列；执行记录独立限高并双向滚动。
- 启动 prompt、完整节点列表及长材料默认折叠。
- 模型配置按钮打开按 Role / Judge 列出的配置面板；按角色编辑主备，不把完整表单常驻首屏。

### Q5：以新派发为生效边界

- 保存成功后，目标角色下一次新登记的派发采用最新配置；包括同节点返工、恢复和 Judge 再次判定，不仅是下一个节点。
- 已经安排登记的派发保持原路由，即使尚未发送；当前在途请求不热切换。
- 场景：A 在途时保存 C/D，A 随后发生允许自动恢复的模型故障。安全收口后的新派发先用 C，不跳过 C 回旧 A/B，不消耗未使用的新备用机会。
- 其他故障沿用原安全规则；保存配置不自动解除 BLOCK，不撤销已接受结果。

### Q6：备用延续

- 新主 C 发生合格故障后使用新备 D；D 成功后后续使用继续沿用 D，直到再次明确更新模型配置。
- 普通恢复、后续节点与进程重启不自动回主，也不重置恢复轮次。
- 主动同值更新、仅修改备用也让下一次新派发重新从主模型开始，按 Q10 开启新恢复轮次；同一次请求的网络重试不重复重置。

### Q7：手动工具与 GUI 统一语义

- `workflow_set_role_model` 的手动指定模型改为更新角色的 Run 主模型，并保留最新备用配置，不再隐式回到最初冻结主备。
- GUI 与工具使用同一规则；工具仍仅允许该 Run 的固定 Manager 调用。
- 工具省略思考强度时沿用已有的“该模型默认档位”语义，不继承旧档位。

### Q9：人类写入与保存边界

- 通过 GUI 身份校验的人可修改选择器明确选中的未结束 Run，包括其他工作区的 Run；界面清楚显示目标 Run 与工作区。
- completed / terminated Run 只读。目标失效则拒绝，不回退另一个 Run。
- 一个角色的主备及独立思考强度作为一组原子保存；校验失败不部分生效。
- 人或工具并发修改同一份模型配置时提示冲突，不静默覆盖。
- 保存不打断在途执行，不自动恢复 BLOCK，不新增终止或推进权限。
- 这是独立的人类写入授权，不是冒充 Manager 调用工具；[ADR-0006](../adr/0006-current-run-model-configuration.md)已记录对 ADR-0005 只读范围的局部修订。

### Q8：原会话换模，修订方案已确认

用户明确质疑“换模型就必须重建子代理、丢完整历史”，期望仅对选中未结束 Run，在 Role 下次接受任务时直接切换该子代理的模型，并保留其上下文。前一轮 fresh replacement 推荐源自插件现有策略，不能当作宿主硬限制；该推荐撤回，未成为已确认设计。

只读核查发现：

- 本机[安装包版本](<C:/Users/hua/AppData/Roaming/fnm/node-versions/v24.16.0/installation/node_modules/@deepseek-ai/dsh/package.json#L4>)为 `0.2.1-rc.5`；宿主源码 checkout 为 `0.2.1-rc.2`。下述关键证据来自安装产物，不等于确认当前运行进程已加载该版本。
- 公开 [installModelSelection](<C:/Users/hua/AppData/Roaming/fnm/node-versions/v24.16.0/installation/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-agent/lib/index.js#L148-L209>)支持同 Session 后续请求使用新的 provider / model / reasoningEffort，不清空历史；未指定档位会清除旧继承档位。它本身按请求步骤生效，插件须把应用时机约束到 Q5 的新派发边界，而不是保存时立刻改在途 Agent 的选择。
- 不是已有单调用的子代理 setter：普通 GUI 的 selectModel 拒绝子代理且会影响全局默认，不能直接复用该入口。可使用正式 helper 与 [agent/created 生命周期钩子](<C:/Users/hua/AppData/Roaming/fnm/node-versions/v24.16.0/installation/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-agent/lib/types/runtime-types.d.ts#L214-L231>)，在新/冷 activation 放行排队任务前恢复目标选择；同一 Agent 不得重复安装 helper。
- helper 的选择引用只在内存；子代理[冷恢复](<C:/Users/hua/AppData/Roaming/fnm/node-versions/v24.16.0/installation/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-subagent/lib/index.js#L2141-L2189>)仍从初始 descriptor 构造路由。因此 Run 需持久化配置、派发需固定本次路由，冷恢复需重新应用，不能误以为写一次内存选择就跨重启自动保持。
- 保留的是同一个 Session 及其规范化历史；既有 compact 仍生效，跨 provider 不承诺原生推理状态、缓存或所有消息类型逐字无损。还需集成测试验证 preset 顺序、冷恢复、档位清除及目标模型能力。

**已确认：仅因模型变化不新建 Session；可复用的子代理保留 Session 身份及上下文，在下一次安全派发前应用所选模型。原有 `reuse: node` / `continuable` 和 Judge 正常会话生命周期不变，不借换模功能强改整个 Run 的复用策略。** 该问题不改变 Q5：在途及已登记派发不改。核查仅确认源码级可行性，不代表功能已实现或真实 Host 测试通过。

## 第三轮最终决定

### Q10：每次主动更新都从最新主模型重新开始

- 按钮为“更新，下次从主模型开始”；仅修改备用、思考档位或主动同值提交，也授权新一轮主→备。
- 不另加“重试主模型”按钮；保存后仍等待下一次新派发，不能自动解除 BLOCK。
- 同一次提交的网络重试不重复授权；新配置可以覆盖尚未使用的旧待生效配置。连续更新 C/D 后又更新 E/F，下一次新登记派发从 E 开始。
- 未修改的角色不受影响；普通轮询、恢复或进程重启不是主动更新。

### Q11：完整主模型、可清空备用、独立档位

- 主模型显示当前解析的完整路由并必填；显式提交该路由，不增加“恢复模板配置”功能。
- 备用可清空，代表禁用，不回填冻结备用或自动选择其他模型。
- 两路档位分别选择，可用“模型默认”；目标模型不支持的配置应在保存时明确拒绝，原配置不部分修改。

### Q12：保护编辑草稿

- 轮询只更新状态，不覆盖编辑草稿。
- 有草稿时切换 Run 或关闭面板，提示放弃或继续编辑。
- 配置冲突保留草稿，用户核对最新配置后再提交；不静默覆盖他人的更新。

### Q13：不做变更记录或审计

- 不新增模型配置变更记录、历史列表或审计界面，也不为此扩展存储。
- 仍显示当前配置、待生效状态及各执行记录实际使用的模型；后者是既有执行事实，不是新增配置审计。
- 正确执行所需的配置版本、去重与故障轮次状态不是审计功能，不能因为取消审计而省略并发和派发安全。

### Q14：直接更新本次 Run，没有额外迁移操作

- 用户只需选择尚未结束的 Run 和角色，修改后提交；该角色下一次新派发使用更新后的主模型。
- 不提供或要求“首次更新”“升级”“迁移”“启用新模式”等步骤，不设置用户需要理解的两套更新方式。
- 未修改的角色、其他 Run、模板及已登记的派发保持不变。持久化兼容是实现内部责任，不转化为用户操作。

设计问题已收敛；此处确认的是产品行为，不授权实现、部署或修改真实 Run。

## 接入约束（源码调研，不代表实现或验证完成）

- 换模型与会话生命周期分别处理：普通 Role 原有 `reuse: node` / `continuable` 规则、Judge 新判定或 followup 规则，不因新增配置界面而暗中改变。保留 Session 不代表绕过既有边界 compact 或承诺历史逐字永不压缩。
- 当前复用路径只排队 prompt，[Host adapter](../../src/plugin/host.ts#L271-L282)没有对复用 Session 应用新模型；Q8 已核实正式宿主入口，实施需接入并验证该入口，不能只删除 active-role 禁令。维持原 subagent manager 的 ownership，不绕开它创建第二个同 ID activation。
- [派发 freshness 检查](../../src/engine/engine.ts#L640-L649)包含整行版本，保存配置也更新整行版本；新方案不能让单纯保存配置使既有派发回执失效，也不能用旧 Run 副本提交回执覆盖新主备。
- 目前派发模型快照不是完整的 Host 输入合同：[Actor 新建](../../src/plugin/host.ts#L400-L415)与[Judge 新建](../../src/plugin/host.ts#L429-L455)会从 Run 再解析路由。新方案必须将登记时确定的路由贯通新建和复用派发，避免“快照记旧模型、实际请求用新模型”。配置更新时间与旧派发失败处理也必须区分，不能消耗未实派新配置的恢复机会。
- 已有测试中“人工设置必须 fresh”与“在途旧模型失败消耗未实派人工轮次”的断言是现行策略证据，不是新需求不可实现的证据；后续实施应按最终合同调整，并保留身份、收口、历史归因及持久化测试。

## 实施范围与验收标准（尚未执行）

沿用现有监控组件、主题、表格、路由校验和 Host 适配层；不加表格依赖，不重写工作流引擎，不增加审计或迁移产品功能。故障资格与安全恢复仍按[现行备用模型规格](../specs/role-model-fallback.md)，不把业务 REJECT、鉴权/参数错误或未知故障泛化为自动切备。

| 场景 | 必须满足 |
| --- | --- |
| 宽屏 / 窄侧栏 / 低高度，明暗主题 | 宽屏概览两列、窄屏堆叠；层次清晰，文字、控件与内容不被宿主裁切 |
| 短表 / 长表 / 长字段 | 短表自然高度；长表有限高度，表内双向滚动，表头及身份列可见，最后列和最后行均能到达 |
| 在顶部记录查看末尾字段 | 无需先滚到全部记录最底部；横向滚动条位于记录窗口底部，窄屏固定列不遮满可视区 |
| 轮询与编辑 | 保留记录选择、滚动位置和未保存草稿；完整详情仍可查看，切换 Run 不误提交旧草稿 |
| A 在途或已登记时更新 C/D | A 不变且回执不丢；下一次新登记派发使用 C，监控记录与实际请求一致 |
| Role 复用 / Judge followup | 换模不额外更换 Session ID，不额外丢上下文；既有 compact 与正常会话生命周期仍有效 |
| C/D 的故障恢复 | C 合格失败才用 D，之后沿用 D；旧派发失败不能耗用新配置的备用机会 |
| 同值 / 仅备用 / 连续更新 | 每次主动提交让下次从最新主模型开始；同请求重试不重复重置；清空备用后不再使用旧备用 |
| BLOCK / 终态 / 目标失效 | BLOCK 可保存但不自动恢复；终态不可写；失效 Run 拒绝，不回退到其他 Run |
| 并发配置与派发结算 | 冲突不静默覆盖，草稿保留；结算不覆盖最新配置，配置保存不撤销有效派发身份 |
| 持久化与冷恢复 | 保存后未实派及已实派两种情况下重启，都保留目标配置及故障阶段，恢复时使用正确路由 |
| 隔离范围 | GUI 与 Manager 工具同语义；不改 Manager、未修改角色、其他 Run、模板、冻结定义或历史实际模型 |

静态逻辑测试需覆盖派发边界、路由与版本归因、幂等提交、授权、冷恢复及主备阶段；真实 Host 检查覆盖同 Session 换模、档位清除和跨 provider 消息兼容；真实 GUI 检查覆盖滚动、布局和草稿交互。不能以静态 CSS 文本断言替代真实 GUI 验证。
